# Браузерный конструктор персонажей

Версия спецификации 0.1. Проект к реализации.

Конструктор собирает VRM 1.0 из подготовленных деталей. Игрок выбирает стиль и архетип, меняет детали и палитру, смотрит результат в движении, сохраняет рецепт и скачивает модель. Первый пакет описан в [Minimalist Faceless Fantasy](AVATAR-STYLE-FACELESS-FANTASY.md). Новый стиль на поддерживаемом риге добавляется данными и моделями через тот же интерфейс.

## Ответственность приложений

| Компонент | Ответственность |
| --- | --- |
| EKZA Studio | Отдельный клиентский маршрут `/avatar-builder` и изолированный TypeScript-модуль. Стек Studio (React и Three.js) для интерфейса и сцены. Общий VRM-экспорт через `@ekza-studio/io/write`. |
| OMOBA Workshop | Вход в конструктор с игрового портала. Ссылку из Workshop можно добавить после проверки первого закрытого билда. |
| EKZA Hub | Сохранение загруженного VRM как ревизии, публикация, сборка версии под профиль игры, допуск точного файла в каталог. |
| OMOBA | Проверка игрового GLB и права экипировки, загрузка через существующий SDK, игровые анимации и отображение в матче. |
| Solana | Опциональный выпуск NFT для конкретной сохранённой версии после проверки прав на материалы. |

Конструктор хранит внешний вид. Игровые классы, навыки, оружие, параметры боя, коллизии, подсветка команды и туман войны остаются в ведении OMOBA. Архетип задаёт начальную комбинацию и подсказывает образ для предпросмотра. Профили игровых файлов и сокеты определяются контрактом игры. ## Пакет стиля

Пакет — декларативный манифест с ассетами. Пара `styleId` и `styleVersion` адресует один неизменяемый выпуск. Добавление или изменение детали, палитры, пресета, рига или правил выпускается новой версией стиля. Версия схемы описывает структуру данных. Версия стиля описывает содержимое каталога.

| Поле манифеста | Назначение |
| --- | --- |
| `schemaVersion` | Целое число. Для описанной схемы значение `1`. |
| `styleId`, `styleVersion` | Стабильный ID стиля и положительная целая версия выпуска. |
| `labels` | Название и описание на поддерживаемых языках интерфейса. |
| `rigs`, `bodies` | Поддерживаемые пары ID и версии рига, базовые модели тела, их зоны скрытия и ссылки на проверенные файлы. У каждого тела указан один точный риг. |
| `slots` | Упорядоченный список слотов. Для каждого заданы ID, подпись и обязательность. Один слот принимает одну деталь. |
| `parts` | Массив деталей. Каждая занимает один слот и указывает допустимые тела. |
| `paletteChannels`, `palettes` | Список каналов и палитры с ID и по одному значению на канал. |
| `defaultArchetypeId` | Архетип, который открывается при первом выборе стиля. |
| `archetypes` | ID, подпись, описание, `bodyIds`, `paletteIds`, таблица разрешённых значений `partIdsBySlot` и начальный выбор `defaults` с телом, деталями и палитрой. |
| `rules` | Декларативные зависимости и конфликты между деталями. |

ID технических сущностей состоят из строчных латинских букв, цифр и дефисов. Удалённый ID сохраняет прежнее значение внутри старых выпусков. Каждый двоичный ресурс указывает SHA-256, размер и путь относительно опубликованного пакета. Индекс Studio сопоставляет ID и версию с путём манифеста и его SHA-256. При загрузке проверяются манифест и каждый использованный файл. Пути ресурсов относительны, разрешаются внутри каталога выбранного пакета и исключают внешние адреса и выход за его пределы. Размеры и хеши сверяются до передачи модели на разбор. Архив выпущенных пакетов обслуживается по тем же зафиксированным ссылкам. Импорт рецепта принимает только поля заявленной схемы и ссылки по ID.

### Риги, тела и детали

- `rigId` и `rigVersion` закрепляют дерево суставов, их порядок, T-позу, bind-трансформации и точки крепления. Перенос деталей между ригами требует отдельной подгонки даже при одинаковых названиях костей.
- Каждое тело содержит один базовый меш или несколько именованных частей. Имена зон скрытия закреплены ригом и телом. Деталь может скрыть согласованные зоны, чтобы под туникой или обувью не проступала базовая геометрия. Целиком включённая зона сохраняет корректные швы с соседними частями.
- У детали есть стабильный `id`, `slot`, список `bodyIds`, ссылка на GLB, тип крепления, соответствие материалов каналам палитры, `hideRegions`, сведения об авторе и лицензии. Список тел задаётся явно.
- Тип `skinned` использует веса общего рига. При импорте индексы суставов сопоставляются с закреплённым порядком рига, веса проверяются и нормализуются. Тип `rigid` задаёт известный сокет и локальную трансформацию. В MVP жёсткие детали можно записывать как меши с весом 1,0 на соответствующей кости, используя общий VRM-экспорт.
- Палитра задаёт sRGB-значения `#RRGGBB` для именованных каналов. В MVP игрок выбирает целую палитру. Цвет канала переводится в линейный RGB для `baseColorFactor`. Поддерживаются базовый цвет, встроенная текстура базового цвета, параметры альфа-канала и двусторонность, которые умеет сохранять writer Studio. При переносе текстуры декор пишется через `assetMaterials` с `paletteId: null`, а перекраска обновляет её `baseColorFactor`. Материал с дополнительным обязательным свойством требует расширения экспортного контракта. Для каждого меша превью получает собственный экземпляр материала.
- Портативный выход имеет один риг VRM 1.0 в исходной T-позе, стандартное направление +Z и 15 обязательных humanoid-костей. Метаданные VRM включают имя сборки, авторов выбранных ассетов и условия использования. Публикуемый выпуск закрепляет точные значения метаданных. Разрешения на модель определяются правами на все выбранные ресурсы. Все объявленные humanoid-кости входят в skin, размещённый в Scene0. Материалы первой версии используют совместимое подмножество PBR и unlit. Для первой версии плащи работают на скиннинге, движение дополнительных деталей проверяется на игровых клипах. [VRM 1.0](https://github.com/vrm-c/vrm-specification/blob/master/specification/VRMC_vrm-1.0/README.md) · [Правила humanoid](https://github.com/vrm-c/vrm-specification/blob/master/specification/VRMC_vrm-1.0/humanoid.md) · [Экспорт Studio](guides/characters-to-ekza.md#3-export)

### Совместимость

Сборка последовательно проверяет принадлежность детали слоту, совместимость с телом и ригом, разрешение в архетипе и межслотовые правила. Правило `requires` применяется, когда выбран `partId`. В слоте `slotId` тогда должно быть значение из `oneOf`. Правило `excludes` запрещает одновременный выбор обоих перечисленных ID. Все правила применяются вместе.

```json
[
  {"kind": "requires", "partId": "quiver", "slotId": "outerwear", "oneOf": ["short-poncho"]},
  {"kind": "excludes", "partIds": ["floating-halo", "wide-brim-hat"]}
]
```

В `partIdsBySlot` и в `oneOf` допустим явный `null` для необязательного слота. Все ссылки разрешаются внутри одного выпуска. Архетип задаёт собственные допустимые тела и палитры. Его `defaults` обязаны давать действительный рецепт.

Решение о скрытии зон вычисляется по объединению `hideRegions` выбранных деталей. Известные пересечения, например длинный плащ с колчаном, фиксируются в правилах конкретного стиля. Проверка каталога выявляет битые ссылки, повтор ID, недопустимые зоны, некорректные палитры и пресеты без валидной сборки. Деталь, которая ломает текущую комбинацию, недоступна с кратким объяснением. Несогласованные изменения применяются только как явно выбранный совместимый пресет или новая сгенерированная комбинация.

## Сохранённый рецепт

Рецепт закрепляет конкретный выбор. Его можно скачать, открыть снова и собрать по тому же выпуску каталога. Пример для Воина из первого пакета.

```json
{
  "schemaVersion": 1,
  "styleId": "faceless-fantasy",
  "styleVersion": 1,
  "rigId": "faceless-humanoid",
  "rigVersion": 1,
  "bodyId": "base",
  "archetypeId": "warrior",
  "parts": {
    "headwear": "angular-hood",
    "torso": "layered-combat-tunic",
    "outerwear": "asymmetric-long-cape",
    "head-accessory": null,
    "back-accessory": null
  },
  "paletteId": "warrior-red"
}
```

Все объявленные слоты присутствуют. `null` разрешён только в необязательном слоте и означает явное отсутствие детали. Версия каталога закрепляет все файлы и палитры по хешам. Имя работы, время сохранения, аккаунт и seed могут храниться рядом с рецептом как метаданные черновика. `archetypeId` входит в рецепт, поскольку управляет разрешёнными комбинациями. Игровой класс и оружие задаются в OMOBA. Сведения о кошельке принадлежат операции выпуска NFT.

При неизвестной схеме или недоступной ревизии Studio показывает причину и даёт сохранить исходный JSON. Если в новой версии есть замены, Studio предлагает перенести выбор в новый рецепт и показывает изменения до применения. Сохранённые и опубликованные модели продолжают ссылаться на зафиксированную ревизию. Устаревание каталога и отзыв допуска модели в игру обрабатываются отдельно.

Если адаптеру нужна идентичность рецепта, используется SHA-256 канонического JSON рецепта. Хеш экспортированных байтов хранится отдельно. Повторный экспорт сверяется при зафиксированных версии экспортёра, входных ассетах и параметрах метаданных. Обновлённый экспортёр может дать другой файл из того же рецепта. Уже опубликованная ревизия сохраняет исходные байты. [RFC 8785](https://www.rfc-editor.org/rfc/rfc8785.html)

## Сборка и генерация

1. Архетип открывает авторский начальный рецепт. При выборе другого стиля Studio открывает его начальный пресет и сохраняет предыдущий черновик. Ручная замена проверяется тем же валидатором, что импорт JSON и генерация.
2. Кнопка «Случайный вариант» выбирает совместимые детали и разрешённую палитру для текущего тела и архетипа. Пользователь может закрепить слот перед генерацией. При отсутствии допустимой сборки интерфейс сохраняет текущий выбор и показывает, какие ограничения мешают.
3. Генератор `mix-v1` перебирает незакреплённые слоты в порядке манифеста и отбрасывает заведомо несовместимые ветки. Seed — целое число от 0 до 2³²−1. Порядок кандидатов внутри слота задаёт лексикографический порядок SHA-256 канонического JSON массива `["mix-v1", seed, styleId, styleVersion, archetypeId, bodyId, "part", slotId, candidateId]`. Пустой вариант передаётся как JSON `null`. При равенстве сравниваются канонические JSON-значения кандидатов. Для палитры используются `"palette"` вместо `"part"` и `null` вместо `slotId`. Возвращаются первая допустимая комбинация и первая палитра в полученном порядке. Поиск ограничен 10 000 попыток выбора значения слота на один запрос. При исчерпании этого бюджета возвращается отдельная ошибка и прежнее состояние. Полный выбор сохраняется независимо от версии алгоритма.
4. Сборщик создаёт описание сцены из одного тела, выбранных деталей, скрытых зон и материалов. Превью и экспорт используют это описание, одинаковые веса, сокеты и трансформации. На границе экспорта адаптер преобразует GLB деталей в `CharacterWriteInput` с `SkeletonDesc`, `JointRecord[]`, `MeshData` и `SkinWeights`. Сопоставление суставов выполняется по уникальным стабильным именам из рига с проверкой bind-трансформаций. Материалы сопоставляются с примитивами и каналами каталога. Проверка этого адаптера на теле, одном взвешенном плаще и одном жёстком головном уборе входит в первый прототип. Ракурс, освещение и текущая поза просмотра принадлежат только превью. [Входной контракт writer](../packages/io/src/types.ts)
5. Превью использует общие проверочные движения. Экспорт восстанавливает T-позу, записывает VRM через существующий writer, перечитывает файл для проверки и вычисляет хеш. При загрузке нового выбора прежние временные GPU-ресурсы освобождаются. Если ассет не загрузился, экспорт блокируется с указанием детали.

## Проверка перед публикацией

| Этап | Критерий |
| --- | --- |
| Каталог | Каждый пресет загружается, его ссылки и правила проходят проверку. Для каждого доступного варианта есть допустимая сборка. Сохранённые рецепты сохраняют выбор после смены версии активного каталога. |
| Браузер | Гость собирает, генерирует, сохраняет и повторно открывает все четыре пресета. Отдельные сценарии проверяют одинаковый seed, закреплённый слот, пустой необязательный слот, несовместимую деталь, недоступную ревизию и прерывание загрузки. |
| VRM | Экспорт проходит обратный импорт, VRM-проверки Studio, граничные проверки профиля и проверку Khronos. Проверяется соответствие деталей, материалов и T-позы. SHA-256 совпадает при повторе на зафиксированном экспортёре с теми же входами. [glTF Validator](https://github.com/KhronosGroup/glTF-Validator) |
| Игра | В `omoba-bevy` проверяется скелет исходника. Hub строит игровой GLB по действующему профилю `desktop/humanoid-glb-v1` с клипами `idle`, `walk`, `attack`, `cast`, `death`. Два клиента видят одну одобренную ревизию при первом входе и повторном запуске из кеша. |
| Читаемость | В браузере и на игровой камере проверяются швы, плащи и аксессуары в `idle`, `walk`, `run`, `attack`, `cast`, `death`. На телефоне проверяются силуэт, размер тела, положение HUD, командные индикаторы, туман войны и стоимость отрисовки. |

Локальная проверка скелета из корня `omoba-bevy`. После неё файл проходит сборку и допуск через Hub. Для пилота нужно подтвердить на тестовом файле, что выбранная ревизия сборщика поддерживает VRM 1.0, включая нормализацию направления и ретаргет клипов. Сквозной тест можно пройти в локальном или согласованном тестовом контуре Hub.

```bash
cargo run --offline -p omoba-passport --bin validate-runtime-vrm -- /path/to/avatar.vrm
```

## Добавление стилей

1. Задать новый `styleId` для самостоятельного художественного направления. Выпустить описание силуэтов, палитр и материалов вместе с каталогом деталей, пресетами и условиями использования.
2. Выбрать проверенный риг. Если новые пропорции требуют изменения костей, позы или сокетов, объявить новую версию рига или отдельный ID и доказать посадку каждой совместимой детали. Для этого профиля повторить VRM-проверку и просмотр игровых движений.
3. Положить пакет в каталог Studio, где он загружается тем же механизмом. Браузер строит список стилей, слоты, палитры и пресеты по манифесту. Изображения деталей и подписи обновляются с выпуском стиля.
4. Для проверки архитектуры добавить второй небольшой пакет на том же риге с собственной палитрой, пресетом и составом слотов. В тесте меняются только данные каталога и ассеты. Все прежние рецепты собираются с исходным выбором и хешами на зафиксированном экспортёре.
5. Если новый стиль требует генерации геометрии или новых типов креплений, вводится явная версия возможностей сборщика. Совместимость с браузером и целевым профилем проверяется на отдельном примере. Варианты первой версии собираются из подготовленного каталога.

### Подключение пакета в Studio

1. Добавить свою папку в `packages/avatar-builder/src/styles/`. Каталог реализует `StylePack` из общего `types.ts` и задаёт ID и версию выпуска, подписи, архетип по умолчанию, слоты, палитры и правила.
2. Указать риг. Если меняется bind-поза, использовать новый ID или новую версию рига. Все пакеты с одной парой `rigId` и `rigVersion` используют одинаковую иерархию, порядок и позиции суставов. Базовый контракт VRM перечислен в `src/rig.ts`.
3. Подключить сборщик геометрии через `StyleDefinition.buildGeometry(recipe, palette)`. Входы берутся из каталога этой версии. Сборщик возвращает новые экземпляры мешей в мировых координатах bind-позы с цветом и суставом. Демонстрационные предметы помечаются `previewOnly`, свечение превью задаётся `previewGlow`.
4. Добавить одну запись в [реестр стилей](../packages/avatar-builder/src/styles/index.ts). Интерфейс покажет переключатель, когда в реестре есть несколько стилей. Каждый стиль восстанавливает свой черновик. Экспорт берёт риг и имя из выбранной ревизии.
5. Оставить старую запись в реестре при выпуске новой ревизии. Новая сборка открывается с последней версией, импорт старого JSON возвращает его закреплённую версию. Проверки новых пакетов запускаются командой `pnpm --filter @ekza-studio/avatar-builder test`. [Тест второго пакета](../packages/avatar-builder/test/style-registry.test.ts)

| 1. Сквозной прототип | Один риг и тело, три слота (головной убор, торс и верхний слой), по два варианта и две палитры. Один экспортированный скин через Hub появляется на двух клиентах OMOBA. Подойдёт согласованный бесплатный пилотный ассет. |
| 2. Первый пакет | Все четыре художественных пресета, опциональные головной и спинной аксессуары, сохранение и импорт рецепта, управляемая генерация, проверка второго пакета без правок сборщика. |
| 3. Личный гардероб | Сохранение в аккаунте и возобновление редактирования. Если скин должен носить только владелец, требуется подтверждаемое право экипировки, серверная проверка в матче и раздача той же версии остальным клиентам. У бесплатной публичной публикации доступ общий. |
| 4. Минт | Опциональный выпуск для одобренной неизменяемой ревизии с хешами рецепта и модели, PNG и ссылками на сохранённые файлы. Владелец подписывает выпуск в кошельке. Допуск проверяет игра через текущий канал своей публикации. |

При первой проверке публикации используются существующие одобрение и игровой профиль. Для массовой персонализации потребуется отдельное решение о допуске комбинаций, проверяемых на сервере по разрешённым деталям. Действующий Solana-минтер связывает один URI метаданных с каждым шаблоном. Для пробного уникального выпуска подходит шаблон с тиражом 1. Массовый выпуск индивидуальных рецептов требует проектирования отдельного потока.
